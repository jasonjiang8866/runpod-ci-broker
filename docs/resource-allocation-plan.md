# 资源查找、任务分配与求解器接入计划

2026-11-17（新加坡时间）。目标：在用户明确的预算、兼容性和等待上限内，
缩短取得可用 GPU 的时间，并提高任务完成率。范围限定 RunPod Pods + GitHub Actions。

## 基线与实施顺序

主线已有两次真实 GPU smoke 验收及清理证据；这些验证了固定实验的生命周期。
PR #21 提供只读查找、候选队列和模拟容量反馈，目前没有实测其租卡成功率提升。
本计划依次推进以下三个阶段，并从第一阶段开始落地。

| 阶段 | 交付物 | 验收条件 |
|---|---|---|
| M1：查找与真实创建反馈 | 统一规划接口、持久化尝试记录、通用单任务控制器 | 查询→选择→创建→就绪→产物→清理有证据；容量拒绝可换候选；未知创建先核对；所有尝试共用原预算 |
| M2：多任务队列 | 优先级、等待老化、统一预算与并发槽、可靠领取/恢复 | 并发控制器不会重复领取；重启不重置预算；灵活任务不会无谓阻塞硬件限定任务 |
| M3：优化求解器 | 可选 MILP／约束规划适配器、隔离执行、基线对照 | 同一输入/事件序列比较可行性、目标值、耗时和完成任务数；超时与无解可控；真实收益另行验证 |

### M1a：统一接口（PR #22）

1. 定义纯规划接口及排序基线。输入是经过硬约束过滤的候选，输出只能引用
   输入中的任务与候选 ID。独立验证预算、槽数、每任务至多一个分配和快照身份。
2. 查找器、模拟器和真实控制器的可选路径使用同一接口。真实控制器在创建前
   检查快照完整性、观察时效、当前作用域资源以及最终候选。
3. 把求解结果、创建确认/容量拒绝/其他拒绝/未知结果、请求耗时、请求机房与
   实际机房、认证就绪耗时写入现有日志。未知值保留空值。
4. 使用真实 Controller 代码、SQLite 条件日志和假云端做端到端离线验证。
   验证求解器输出异常、过期方案、持久化失败和丢失响应均不会产生重复创建。

本次不改变历史 campaign 的身份、预算、一次创建上限或恢复规则。新路径通过
Controller 的 `search_policy` 参数或 `start --search-policy PATH` 显式选择；现有
付费工作流不新增触发方式。固定 campaign 不因反馈而获得第二次创建资格。

### M1b：通用单任务控制器与付费验证

**M1 单任务付费验收已通过。** 11 月 18 日的全球查找在首次创建时租到 RTX 4090，
worker 就绪、CUDA 显存读写、结果上传回执和 Pod 删除均已验证，独立恢复也已通过。
详见[本次付费验收](bounded-allocation.md#november-18-paid-regression)。
[11 月 17 日的 PRO 6000 Server 启动失败](allocation-regression-20261117.md)仍待定位。
下一里程碑为 M2 多任务队列与统一预算，M3 继续保留求解器接口。
`allocation.BoundedController` 将新的任务身份、预算和执行窗口从历史 campaign
中分离；目前工作负载仍限定为已发布的固定 GPU smoke。它通过相同的
`PlacementSolver` 接口选择候选，没有增加 MILP 依赖。详见
[控制器使用与验收边界](bounded-allocation.md)。

离线测试覆盖容量拒绝换卡、403、响应丢失、持久化失败、取消、结果与上传回执、
清理失败和恢复接管。测试使用注入的假云端，不构成真实 GPU 或成功率证据。
手动入口只读取已提交的固定验收配置，并核对历史清理及累计预留；恢复入口
核对原始 dispatch 身份，不具备创建权限。扩展 worker 已发布并固定新镜像；
本次清理后验收配置已关闭，旧任务不能获得新的创建机会。

- 把任务授权、执行窗口和多次尝试预算从历史 campaign 常量中分离，使用同一
  作用域条件日志保存全部候选尝试和保守费用预留；重试不能重新获得预算。
- 接入有总时间/HTTP 次数上限的查找循环。创建前重新检查库存和候选；明确容量
  拒绝写入冷却历史后才允许换候选；403、账户限制和创建结果不明分别处理。
- 为每次创建保留独立 intent 和身份，确保单个任务同时至多一个未解决的创建。
  未知结果必须先核对；超时、取消和恢复都进入可验证的清理路径。
- 保持已验证 worker 的固定 smoke 工作负载，先验证通用租卡调度，再扩展模型训练。
- 完成代码、CI、镜像与恢复检查后，准备具体付费试验规格：允许卡型、预算、
  时限、次数、输入版本、结果和清理门槛。新的付费试验使用单独有效的授权。

M1 的付费验收至少包含一次真实查找→创建→认证就绪→GPU smoke→结果导出→确认删除。
自然发生容量拒绝时验证反馈；没有拒绝就不声称真实换卡已验证。离线故障注入
覆盖失败分支。一次成功只证明流程可行，不能证明成功率提高。

### M2：多任务队列与统一资源账本

- 每个任务保留独立约束、优先级、入队时间、最晚启动时间和运行时长上限。
- 用条件写入完成领取与费用预留；所有活动任务共同占用预算和并发槽。
  明确本次作用域是一个中央 Broker，不能用不同仓库的 Actions concurrency
  代替跨仓库互斥。
- 重启从日志恢复；活动和未知创建占用并发槽；已完成任务不能被重新执行。
- 先实现确定性队列策略，覆盖优先级、等待老化和硬件稀缺性。保留相同输入的
  规划快照，供后续优化器离线重放。

验收案例：一个仅可使用 5090 的任务、一个可使用 4090/5090 的任务、一个可使用
3090 的任务；在可验证的资源约束下比较分配。另测并发领取冲突、预算耗尽、
迟到任务、饥饿保护和控制器崩溃恢复。库存等级不能充当精确的 GPU 数量。

### M3：可选优化器与实验设计

- 首先给出明确目标，例如优先满足高优先级任务，再降低预计等待和费用。
  不把不同单位直接相加；权重、归一化及缺失预测必须明确。
- 定义二元任务—候选分配变量，以及确有需要时的时间/并发变量。保留 CPU 基线，
  在匹配同一约束集的前提下比较 MILP 与约束规划，不预先指定获胜方法。
- 求解器适配器在独立进程执行，使用硬时限和内存界限；独立检查可行解。
  记录 feasible / optimal / infeasible / timeout、求解时长及有效的界限/gap。
  超时有可验证可行解时按明确策略采用，否则回到确定性基线或等待。
- 使用固定合成案例和真实匿名事件重放；报告任务数量、约束、随机种子、解质量、
  求解耗时以及相对基线差异。真实对照需时间分块/交错实验，控制库存随时间变化。

## 预留接口：规划与执行分离

`optimization.py` 提供 `PlanningProblem`、`PlanningJob`、`PlacementOption`、
`SolverResult` 和 `PlacementSolver.solve(problem, time_limit_ms=...)`。
问题可表达多任务、统一费用上限和分配槽数，但当前入口只构造一个任务；
`RankedFirstSolver` 明确拒绝批量问题，没有实现多任务调度或 MILP。

金额使用整数 micro-USD，保守向上取整。当前候选预留费用仍使用已有的“全部
允许尝试按价格上限预留”估计。M2 将由统一账本提供扣除已有承诺后的预算，
并明确既有花费归属，避免重复计算或退款给未知创建。

接口不含 API key、Pod 环境、创建/删除方法或授权修改能力。控制器只从已验证的
原候选中恢复最终方案。更换求解器不能扩大 GPU allowlist、费用、次数或执行窗口。
快照过期、求解失败或无效输出均阻止创建。当前进程内耗时检查只会拒绝迟到结果，
不能中断挂死的第三方求解器；因此在 M3 隔离适配器完成前不能启用第三方求解器。

## 衡量是否更容易租到卡

| 指标 | 口径 |
|---|---|
| 查找到创建确认耗时 | 开始查找到收到有效创建确认；与 worker 就绪分开 |
| worker 就绪耗时 | intent 到认证 readiness 成功；未观测时为空 |
| 容量拒绝 | 仅经过分类的明确创建拒绝；403 和超时不混入 |
| 分配成功率 | 符合条件且实际尝试分配的会话中，在原限制内确认分配的比例；未知单列 |
| 任务验收率 | 完成工作负载、结果验证和清理的比例；不同于分配成功率 |
| 费用 | 预留、观察到的计算费估算、供应商账单分别记录 |
| 资源遗留 | 每个创建的最终状态与独立删除确认；未知保留未解决 |

报告样本数、卡型、约束、时段以及排除原因。目录命中率、模拟通过率和真实
分配成功率必须分别报告；库存 HIGH/LOW 不能伪装成经验成功概率。
