## Investigation and diagnostic correction

The old result-endpoint 403 was **not reproduced**: this attempt ended at
`POST /v2/pods`, before a worker or result endpoint was available.
The [current create API documentation](https://docs.runpod.io/api-reference-v2/pods/create-a-pod)
distinguishes 422 validation failures from 400 placement/rule refusals. LOW catalog
capacity is advisory. Neither the catalog nor `invalid_request` proves that this
failure was capacity-related. The submitted fields match the documented create
contract; there is no evidenced field correction to make from this response.

The adapter discarded the exact status, headers and body. That information cannot
be reconstructed after the run. The follow-up patch preserves `create_http_failure`
with the numeric status, fixed header categories, ambiguity and an unverified
response origin in the journal and JSON/Markdown reports. The error stream is
closed without reading its body, which may echo credentials or Pod environment.
The existing once-only POST, ambiguous-create handling, accounting, cleanup,
workflow permissions and image remain unchanged.

The original 403 source remains unresolved. This patch is an observability fix,
not a claimed transport or allocation fix. A further create is not enabled by it;
repeated dispatch still resumes the existing blocked record. No next paid attempt
is proposed here without first reviewing a concrete plan and its diagnostic limits.

Validation of this diagnostic correction: 340 offline tests passed, including
real adapter/controller/report paths with injected 400/422/403/500 responses,
unreadable error bodies, stream closure, secret omission, retained accounting
and no second POST. Ruff and strict mypy across 24 modules passed. These checks
do not constitute successful cloud allocation or GPU validation.
